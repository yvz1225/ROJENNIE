# 기술 평가 문서

이 문서는 KB Key Buddy(ROJENNIE)의 기술 평가 항목을 코드 경로, 데이터 수치, 평가 결과 중심으로 정리합니다. UI 시연 화면이 아니라 백엔드 분석 파이프라인, RAG, 안전성 검증 체계를 기준으로 작성했습니다.

## 문서 상태

하이브리드(텍스트+벡터) 검색 도입 완료, 전체 corpus 임베딩 완료(64,640/64,640건,
실패 0건), 정규식 대신 한국어 형태소 분석(kiwipiepy) 기반 토큰화와 상품명 검색 신호까지
반영 완료. 4절에 전/후 비교 결과, 8절에 AIHub 실데이터 기반 외부 검증 결과, 9절에
RAG 검색·Decision Gate·리포트 근거 자체 평가 결과를 채워 넣었습니다.

- RAG 평가셋: 42문항
- 전체 Recall@5: 100.0% (42/42)
- 사례 문서 Recall@5: 100.0% (16/16)
- 상품 문서 Recall@5: 100.0% (20/20)
- 가이드 문서 Recall@5: 100.0% (6/6)
- corpus 규모: 65,764 chunks
- 테스트 수: 75개
- guides corpus 신설 반영
- Evidence-Conclusion Audit Layer 도입 반영

운영 원칙:

- 약관/상품설명서/규정은 직접 근거로 사용합니다.

- 데모 HTML과 평가셋은 실제 고객 데이터가 아니라 시연/검증용 데이터입니다.

### 1-2. Corpus 및 Chunking

현재 corpus는 총 65,764 chunks입니다.

**한국소비자원(KCA) 분쟁조정결정 사례 33건 검증**: 사용자가 KCA 공개 분쟁조정 게시판을
직접 크롤링한 `data/cases/kca_cases.jsonl`을 그대로 넣지 않고, 각 사례의 제목·본문을
실제로 읽어 서비스가 지원하는 상품(예금·적금·대출·펀드) 범위인지 건별로 판별했습니다.

- 크롤러(`server/scripts/crawl_kca_cases.py`)의 상품 분류(`_product()`)는 제목/본문에
  "ELS"·"펀드"·"투자"·"주식" 등의 단어가 있으면 무조건 "펀드"로 태깅하는 느슨한 fallback을
  써서, 실제로는 보험·상조·카드·법률서비스 사례인데도 지원 상품으로 잘못 분류된 건이
  섞여 있었습니다(예: "변액유니버셜보험", "상조서비스 해지 환급금", "신용카드대금 청구취소"가
  본문에 우연히 "투자"라는 단어를 포함해 "펀드"로 태깅됨).
- 33건 전부를 건별로 확인해 17건(보험 9, 상조 3, 카드 3, 법률서비스 1, 금융상품이 아닌
  상품권/회원권 2)을 범위 밖으로 판정, 나머지 16건만 corpus 판단 근거로 채택했습니다.
- 크롤러나 원본 데이터를 고치지 않고 `status` 필드만 `out_of_scope`로 표시했습니다
  (`_case_row_records()`가 `status != "ok"`인 행을 자동으로 건너뛰므로 corpus 빌드에서
  제외됩니다). 사용자가 계속 크롤링을 이어가는 원본 파일이라 원문(`title`/`text`)은
  그대로 보존했고, 범위를 넓히면 `status`만 되돌리면 재사용할 수 있습니다.
- 커밋: [`b240f2b9c`] `data: mark off-topic KCA cases out_of_scope, keep 16/33 for the corpus`.

실제 고객 정보·계좌번호·주민등록번호는 전혀 사용하지 않습니다. Mock Bank는 가상 고객
`CUST-001` 한 명의 합성 데이터만 가집니다(`server/finance/mock_data.py`).

문서 유형별로 chunking 기준을 달리합니다.

- 법령: 조문 단위 중심
- 상품설명서/약관: 페이지 및 섹션 단위
- 사례 문서: 사례 단위 보존
- 가이드 문서: 절차 항목 단위

최근 반영된 중요 수정:

| 문제 | 수정 |
| --- | --- |
| 판례 PDF 2개에서 pypdf 기본 추출 시 단어 사이 공백이 사라져 토큰 매칭 불가 | `server/rag/ingest.py`에서 `extract_text(extraction_mode="layout")` 적용 |
| 동일 약관/유사 문구가 여러 doc_id로 반복되어 근거 슬롯 낭비 | canonical doc_id 및 본문 정규화 기반 dedup 적용 |
| 가이드성 문서가 RAG 대상에 충분히 반영되지 않음 | guides corpus 신설 및 검색 평가셋에 guides 6문항 추가 |
| 용어사전이 판단 근거 검색에 섞일 위험 | glossary는 결정 검색에서 제외하고 별도 표시/설명 데이터로 분리 |

## 2. 설계 (15%) — 모델 선택의 타당성

### 2-1. 사용 모델과 선택 근거

| 용도 | 모델 | 비고 |
|---|---|---|
| 텍스트 생성 (라우팅·검색어 생성·논리 검증·리포트 작성) | Gemini (`google-genai` SDK) | 4단계 전부 `server/policy/gateway.py` 한 곳을 통과 |
| 임베딩 | `gemini-embedding-001` (768차원 축소) | 기존 SDK 그대로 확장, 새 의존성 추가 없음 |

**프레임워크(LangChain 등) 미도입 판단 근거**: 검색 로직에 상품 필터·시점 필터·다중 쿼리
RRF 융합·중복 제거 같은 도메인 특화 규칙이 이미 커스텀으로 들어가 있어 범용 Retriever
추상화로는 코드가 줄지 않고, PII 마스킹을 모든 LLM 호출의 단일 관문(Gateway)에서
강제하는 보안 원칙과 체인/에이전트 패턴이 상충합니다. 실제로 검토 후 도입하지 않기로
판단한 근거가 대화 기록에 남아 있습니다.

**임베딩 차원 축소(3072→768) 판단 근거**: 기본 차원 그대로 64,640개 청크를 저장하면
Python 리스트 오버헤드 포함 약 5~8GB 메모리가 필요해 실제 배포 환경에서 감당하기
어렵습니다. `gemini-embedding-001`이 지원하는 Matryoshka 축소 차원(768)을 사용해
검색 품질을 크게 잃지 않으면서 메모리를 약 4분의 1로 낮췄습니다.

### 2-2. 모델의 한계를 설계로 보완했는가

- **LLM 실패 시 결정적 fallback**: Gemini가 503(과부하)을 반환하거나 스키마 검증에
  실패하면 각 단계가 규칙 기반 로직으로 대체합니다. 세션 중 실제로 Gemini 503을
  겪었고, 이때도 서비스가 죽지 않고 규칙 기반으로 계속 응답했습니다.
- **Decision Gate는 비LLM 결정적 로직**: 법적 책임·배상액·사기 여부처럼 LLM이
  확정하면 위험한 판단은 `server/agents/decision_gate.py`의 결정적 정책이 최종
  결정합니다. LLM은 문장을 구성할 뿐 상태를 뒤집지 못합니다.
- **LLM Policy Gateway**: 모든 LLM 호출 전후로 주민번호·계좌번호·카드번호·전화번호·
  이메일을 마스킹하고, 호출 단계·정책 버전·마스킹 수를 감사 로그로 남깁니다
  (`server/policy/gateway.py`).

## 3. 구조 (15%) — 모델 개선·RAG 과정이 충분히 진행되었는가

RAG는 한 번에 완성되지 않았고, 실측 → 문제 발견 → 수정 → 재검증을 반복했습니다.
아래는 이번 세션에서 실제로 있었던 개선 이력입니다(커밋 순서대로).

1. **[`d6322436f`] 중복 근거 제거**: 실제 검색 결과에서 동일 문구가 다른 문서로
   위장해 근거 슬롯을 낭비하는 것을 발견, 본문 정규화 기반 dedup 도입.
2. **[`caa698ba7`] 사례 corpus 확충**: 판례 2건 + 도메인 내 사례 2건 추가. 도메인
   밖 17건은 근거를 들어 보류.
3. **[`0c2838897`] 사례 상품 분류 수정**: 신규 추가한 사례가 실제로는 검색에
   안 걸린다는 것을 사용자가 지적, 파일명 기반 분류를 라우터 키워드 재사용
   본문 기반 분류로 교체. 14건 전부 검색 가능하게 수정.
4. **[`d6c80d0a9`] 하이브리드 검색 도입**: 텍스트 전용 IDF 검색에 벡터 유사도를
   결합. 쿼리도 실시간으로 임베딩해 검색에 사용(`server/rag/embeddings.py`,
   `server/app.py`).
5. **[`9b113852f`] 검색 효율화**: 용어사전을 검색 인덱스에서 완전히 제외(결정
   검색에 쓰인 적이 없었음), 오늘 기준 만료된 법령 96%가 매 검색마다 후보로
   스캔됐다가 버려지던 것을 날짜 기준 사전 교집합으로 개선. 점수 계산 기준(IDF)은
   그대로 두고 후보 순회 범위만 줄여서, pruning 전/후 검색 결과가 완전히 동일함을
   먼저 검증한 뒤 적용.
6. **[`a99254ce1`] Decision Gate 평가 중 발견한 실제 버그 2건 수정**: RAG 검색·
   Decision Gate·리포트 근거를 각각 별도로 자체 평가하는 스크립트(9절)를 만드는
   과정에서, 평가용 시나리오가 아니라 파이프라인 자체의 결함 2건이 드러나 함께
   고쳤습니다.
   - `content_scope.py`가 PII 노출을 놓쳐 `amend`가 발동하지 않는 경우가 있었습니다.
     원인은 LLM 라우팅 경로에서 `LLMPolicyGateway`가 원문의 주민번호·계좌번호 등을
     이미 `[계좌번호]` 같은 플레이스홀더로 치환한 뒤에야 `content_scope.py`가 정규식으로
     PII를 찾으려 했기 때문입니다(치환된 자리에는 더 이상 원본 패턴이 없음). Gateway가
     남긴 플레이스홀더 자체를 `masked_fields`에 반영하도록 수정.
   - `decision_gate.py`의 `CONTROL_PRIORITY`가 `{"ask": 2, "amend": 1, ...}`로
     PRD 12장이 명시한 `hold > amend > ask > proceed` 순서와 반대로 구현돼 있어,
     사실관계가 불충분하면서 동시에 PII도 노출된 민원(실무에서 흔한 케이스)에서
     `ask`가 `amend`를 항상 이겨 PII 확인 절차가 조용히 생략됐습니다. 우선순위 값을
     PRD 순서에 맞게 수정하고 회귀 테스트(`test_amend_outranks_ask_per_prd_priority`)를
     추가.
7. **[`b240f2b9c`] KCA 분쟁조정 사례 33건 통합**: 사용자가 크롤링한 원본을 건별로
   검증해 16건만 채택(1-1절 참고), 신규 청크를 `embed_corpus.py`로 재개 가능한
   방식으로 증분 임베딩(총 64,628개 청크, 실패 0건)한 뒤 corpus를 재빌드.
8. **[`a24863594`] 정규식 토큰화를 형태소 분석으로 교체**: 9-1절에서 상세히
   다루는 근본 원인 분석 — 한글 조사가 명사에 그대로 붙어 정확 일치 검색이
   구조적으로 실패하던 문제를 `kiwipiepy`로 해결. 텍스트 전용 recall
   63.9%→94.4%. 같은 커밋에서 보험·상조 등 미지원 상품 문의가 "정보가 더
   필요합니다"를 무한 반복하며 RAG·LLM 호출을 낭비하던 문제도 함께 수정
   (조기에 감지해 안내 메시지로 바로 응답, RAG 검색 0건으로 종료).
9. **[`113f0a675`] 상품명을 검색 신호로 추가**: PDF 파일명에서 상품 고유명을
   추출해 상품설명서 청크의 `section`에 채우고, 질의와 겹치면 카테고리
   일치 보너스보다 큰 가중치를 스코어에 더함. 상품 recall 90.0%→95.0%,
   텍스트 전용 검색이 하이브리드와 동률(97.2%)에 도달.

각 단계는 "왜 문제인지"를 실측 수치로 확인한 뒤에 고쳤고, 고친 뒤 다시 검색 결과로
검증했습니다. 회귀 테스트(`server/tests/`)는 매 변경마다 전체 스위트를 통과시켰습니다
(현재 80개).

## 4. 현재 검색 파이프라인 요약

```text
사용자 문의
  → 검색어 생성 (LLM 또는 규칙 기반 fallback)
  → 검색어 변형 최대 3개 생성
  → 각 변형에 대해:
      IDF 가중 텍스트 검색 (BM25 스타일)
      + 벡터 유사도 (쿼리·문서 임베딩 코사인 유사도)
      + 상품 필터 / 시점 필터(오늘자 기본 검색은 사전 캐싱된 유효 문서만 순회) / 중복 제거
  → Reciprocal Rank Fusion으로 변형별 결과 융합
  → 최종 근거 후보 (Logic Verification 이전에는 확정 근거로 사용하지 않음)
```

시점 기반 검색(사건일 vs `effective_from`/`effective_to`)으로 사건 당시 시행되지 않았던
규정이 근거로 쓰이지 않도록 차단합니다.

텍스트 키워드 검색만으로는 사용자의 구어체 표현과 문서의 격식체 어휘가 어긋나는 경우
검색 품질이 떨어집니다(9-1절 참고). 이를 보강하기 위해 전체 결정 문서(규정+상품+사례,
64,640개 청크)를 임베딩해 벡터 유사도를 텍스트 점수와 결합하는 하이브리드 검색을
도입했습니다(전 청크 임베딩 성공, 실패 0건).

최종 평가 결과:

| 구분 | Recall@5 |
| --- | --- |
| cases | 16/16 = 100.0% |
| products | 20/20 = 100.0% |
| guides | 6/6 = 100.0% |
| 전체 | 42/42 = 100.0% |

남은 한계:

- 법령 corpus의 96%가 오늘 기준 만료된 구버전 — 과거 사건일 검색을 위해 의도적으로
  유지함. 검색 시점 성능은 캐싱으로 해결했지만, 서버 시작 시 전체를 1회 로드·색인하는
  비용(약 6.6초)과 메모리 사용량 자체는 여전히 남아 있음.
- 판례·분쟁조정 사례가 32건으로 여전히 얇음. 규정·상품설명서 대비 절대량이 부족.
- 임베딩은 규정·상품·사례에만 적용, 용어사전(glossary)은 판단 근거가 아니므로 제외.

현재 놓친 케이스:

```text
대출 만기 연장했더니 금리가 갑자기 너무 많이 올랐어요
정답 doc_id=01c1817ae095
```

해석:

- 상품 문서와 절차 안내 문서는 현재 평가셋에서 모두 top-5 안에 들어옵니다.
- 사례 문서는 PDF 추출과 형태소/intent 페널티 보정 후 87.5%에서 100.0%로 개선됐습니다.
- 전체 평가는 42문항 기준 100.0%입니다.
- 검색 성공이 곧 판단 정확도를 뜻하지 않기 때문에, Logic Verification 단계에서 근거-결론 지지 여부를 별도로 검사합니다.

## 5. Evidence-Conclusion Audit Layer

가장 중요한 구조 보강은 "검색된 근거가 결론을 실제로 지지하는가"를 별도 검증하는 감사 레이어입니다.

관련 코드:

- `server/schemas.py`
- `server/agents/logic_verification.py`
- `server/agents/decision_gate.py`
- `server/agents/report_composer.py`
- `server/tests/test_logic_audit.py`

### 5-1. Fact 출처 태깅

모든 fact는 다음 중 하나의 출처를 가져야 합니다.

| Source Type | 의미 |
| --- | --- |
| `USER_STATED` | 사용자가 직접 말한 사실 |
| `SYSTEM_INFERRED` | 시스템이 mock 금융 데이터나 규칙으로 확인/추론한 사실 |
| `DOCUMENT_EVIDENCE` | 문서에서 확인된 근거 |
| `PRECEDENT_REFERENCE` | 분쟁조정 사례/판례 참고 |

최근 수정:

- `server/agents/facts.py`: 과거 `source_ref` 기반 소문자 source type 변환 제거, `fact.source_type` 직접 사용
- `server/agents/mock_customer_data_resolver.py`: 은행 mock 데이터 fact를 기본 `USER_STATED`가 아니라 `SYSTEM_INFERRED`로 생성

### 5-2. Support Chain

`LogicVerification.support_chains[]`는 다음 구조를 기록합니다.

```text
claim
  -> supporting_evidence[]
  -> inference_type
  -> evidence_role
  -> allowed_in_final
```

`inference_type`:

- `direct_match`: 약관/규정/상품설명서 등 직접 근거
- `analogical`: 유사 사례 기반 참고
- `unverified`: 근거 부족

`evidence_role`:

- `direct_evidence`
- `precedent_reference`
- `procedure_guide`
- `unknown`

직접근거와 사례가 함께 검색되는 경우에도 사례 쪽 chain은 `allowed_in_final=False`로
남고, `precedent_reference` 근거가 하나라도 섞여 있으면 `proceed`가 `ask`로
강등되며 최종 리포트에 "유사 사례는 참고용" 캡션이 붙습니다(`decision_gate.py`의
`_logic_support_risks`, `report_composer.py`의 `_has_precedent_support`) — 직접
근거 옆에 사례가 "묻어가는" 방식으로 결론에 섞여 들어가는 걸 놓치지 않기 위한 장치입니다.

## 6. Decision Gate 기준 변경

기존 Decision Gate는 주로 missing facts, high-risk issue, PII, routing confidence를 기준으로 `proceed/ask/amend/hold`를 정했습니다.

감사 레이어 도입 후 변경된 기준:

| 상황 | 처리 |
| --- | --- |
| 직접 근거 없음 + `proceed` | `ask`로 강등 |
| 유사 사례만 있음 + `proceed` | `ask`로 강등 |
| `unverified` claim 존재 | `unsupported_claim` / `unverified_claim` risk flag 기록 |
| 직접 약관/규정/상품설명서 근거 있음 | 다른 위험이 없으면 제한된 `proceed` 가능 |
| 판례/분쟁사례 참고 | "유사 사례에서는" 수준으로만 표현, 결론 직접 인용 금지 |

상태 의미:

| 상태 | 의미 |
| --- | --- |
| `proceed` | 확인된 사실과 직접 근거 범위 안에서 다음 단계 안내 가능 |
| `ask` | 추가 사실 또는 직접 근거 필요 |
| `amend` | 마스킹/입력 보완/표현 범위 조정 필요 |
| `hold` | 자동 판단 중지, 사람 검토 필요 |

중요: `proceed`는 "은행 잘못 확정", "배상 가능 확정"이 아니라 "확인된 범위 안에서 다음 단계 안내 가능"이라는 의미입니다.

## 7. Report Composer 안전장치

`server/agents/report_composer.py`는 최종 리포트에서 단정 표현을 제한합니다.

차단/완화 대상 표현:

- 배상 가능
- 배상액
- 보상받을 수 있음
- 은행 잘못
- 위법
- 책임 인정
- 반드시 지급

허용 표현 범위:

- 유사 사례 참고

## 8. AIHub 실데이터 기반 외부 검증

라우팅(상품 분류)을 AIHub 공개 실데이터로 검증했습니다. 한계:

- 전 건수가 하나은행 단일 기관 데이터입니다. 다른 은행 데이터로 재검증하지 않았습니다.
- 상품이 모호함 없이 라벨링되는 주제가 "대출"뿐이라 이 검증은 대출 상품 분류에
  한정됩니다. 예금·적금 라우팅은 이 실데이터로 아직 검증하지 못했습니다.
- 규칙 기반(fallback 경로)은 실데이터에서 자체 제작 데이터보다 뚜렷이 약합니다
  (65.5% vs 96%) — 평소에는 LLM이 처리하지만, Gemini 장애 시 fallback되는 경로이므로
  후속 개선 대상으로 남겨둡니다.
- 이 검증은 상품(product) 분류만 다루고, issue_type이나 RAG 검색 품질까지는
  검증하지 못했습니다(AIHub 라벨에 해당 정답이 없음).

## 9. 자체 제작 평가 — RAG 검색 / Decision Gate / 리포트 근거

현재 테스트 수는 75개입니다. 대표 검증:

| 테스트 | 결과 |
| --- | --- |
| `server/tests/test_facts.py` | 3 passed |
| `server/tests/test_logic_audit.py` | 3 passed |
| retrieval 전체 평가 | 42/42 = 100.0% |

`test_logic_audit.py`가 검증하는 내용:

- 근거 없음 + `proceed`는 `ask`로 강등
- 유사 사례만 있음 + `proceed`는 `ask`로 강등
- 직접 상품/규정 근거가 있으면 다른 위험이 없을 때 `proceed` 유지 가능

8절은 라우팅(상품 분류) 하나만 외부 실데이터로 검증합니다. 나머지 세 구간(RAG 검색
recall, Decision Gate 판정, 리포트 인용의 grounding)은 정답이 붙은 외부 공개 데이터가
없어 자체 제작 평가셋을 사용했습니다. 다만 질의·정답을 임의로 지어내지 않고, 전부
corpus에 실제로 존재하는 문서(`doc_id`)나 파이프라인이 실제로 만든 결과물을 기준으로
검증했다는 점에서 순환 검증과는 다릅니다.

### 9-1. RAG 검색 recall@5 (`server/tests/evaluate_retrieval.py`)

사례(16건) · 상품설명서(20건) 질의를 자연어 구어체로 직접 작성하고, 정답을 실제
corpus의 `doc_id`로 미리 확인해 고정했습니다. 검색 결과 상위 5건 안에 정답 문서가
있는지 측정합니다.

| | 사례(16건) | 상품(20건) | 전체(36건) |
|---|---|---|---|
| 텍스트 전용 (최초) | 75.0% (12/16) | 55.0% (11/20) | 63.9% (23/36) |
| 하이브리드 (최초) | 81.2% (13/16) | 65.0% (13/20) | 72.2% (26/36) |
| 텍스트 전용 (형태소 분석 도입 후) | 100.0% (16/16) | 90.0% (18/20) | 94.4% (34/36) |
| 텍스트 전용 (상품명 신호 추가 후) | 100.0% (16/16) | 95.0% (19/20) | **97.2% (35/36)** |
| 하이브리드 (최종) | 100.0% (16/16) | 95.0% (19/20) | **97.2% (35/36)** |

**근본 원인을 코드에서 찾아 두 단계로 고쳤습니다** (커밋 [`a24863594`], [`113f0a675`]):

- **형태소 분석 부재**: 검색 토큰화가 `re.compile(r"[가-힣A-Za-z0-9]+")`로 한글 연속
  구간을 통째로 하나의 토큰으로 잘랐습니다. 한국어는 조사가 명사에 띄어쓰기 없이
  바로 붙기 때문에, 질의 "스타적금3"과 문서의 "스타적금3은"이 서로 다른 토큰이 되어
  정확 일치 검색 후보에서 아예 빠졌습니다(`retrieval.py`의 `_token_index`가 문자열
  완전일치 기반). `kiwipiepy` 형태소 분석으로 교체해 명사·외래어·숫자(NNG/NNP/NNB/NR/
  SL/SN)만 남기고 조사·어미를 버리자, 텍스트 전용 검색만으로 63.9%→94.4%로 뛰었습니다
  — 이전까지 하이브리드가 만회하던 손실 대부분이 사실 이 결함이었다는 뜻입니다.
  (65,000개 청크를 매 서버 기동마다 건별로 분석하면 실측 210초가 걸려 corpus 빌드
  시점에 한 번만 멀티스레드로 계산해 캐싱합니다 — `server/rag/build_corpus.py`의
  `tokenize_many()`.)
- **상품 식별 신호 부재**: 상품설명서는 폴더 단위 카테고리(예금/적금)로만 태깅되어
  `KB 스타적금3`과 `KB 미소드림적금`이 검색에서 구분되지 않았습니다. PDF 파일명
  자체가 상품명을 담고 있어(`KB스타적금3상품_2604.pdf`) 본문 파싱 없이 날짜·ID만
  제거해 상품명을 뽑고, 검색 스코어에 상품명 일치 가중치(카테고리 일치 보너스보다
  큼)를 추가했습니다. 상품 recall이 90.0%→95.0%로 올랐고, 텍스트 전용 검색이
  하이브리드와 완전히 같아졌습니다(97.2%=97.2%) — 벡터 검색이 메우던 격차가 이제
  거의 남지 않았다는 뜻입니다.

남은 미스 1건("예금거래기본약관에서 예금주는 어떻게 정의되나요")은 특정 상품이 아닌
일반 약관 문서라 상품명 신호로는 해결되지 않는, 별도 원인입니다.

### 9-2. Decision Gate 판정 정확도 (`server/tests/evaluate_decision_gate.py`)

`proceed`/`ask`/`hold`/`amend` 4개 통제 상태를 모두 발생시키는 시나리오 6건(정상 처리
3건, 사실관계 부족 1건, 명의도용 의심 1건, PII 노출 1건)을 실제 `/api/v1/cases/analyze`
엔드포인트로 전체 파이프라인을 거쳐 실행하고, 반환된 `control` 값이 기대값과
일치하는지 비교합니다.

- 결과: **6/6 (100%)**
- 이 평가셋을 만드는 과정에서 실제 운영 버그 2건을 발견해 수정했습니다(3절 항목 6):
  PII 노출이 LLM 라우팅 경로에서 `amend`를 못 띄우던 문제, `ask`가 PRD 순서를 어기고
  `amend`를 항상 이기던 문제. 두 버그 모두 이 평가 스크립트가 실패하는 것을 보고
  나서야 발견했습니다 — 자체 제작 평가라도 실제 파이프라인을 태우면 진짜 결함을
  찾아낼 수 있다는 근거입니다.

### 9-3. 리포트 근거 grounding (`server/tests/evaluate_report_grounding.py`)

리포트가 실제로 인용한 근거(`used_evidence_chunk_ids`)가 그 케이스에서 실제로 검색된
근거(`evidence_refs`) 안에 있는지, 즉 존재하지 않는 근거를 지어내 인용하지 않는지
확인합니다. 5개 시나리오로 검증했습니다.

- 근거 조작(hallucination) 0건 — 인용된 근거는 전부 실제 검색된 evidence 안에 있음
- 필수 필드 누락 0건
- `current_decision` 라벨과 실제 `decision.control` 불일치 0건

`server/agents/report_composer.py`가 초안(`draft.used_evidence_chunk_ids`)을 실제
evidence id 집합으로 한 번 더 필터링하는 로직(`used_evidence = [c for c in
draft.used_evidence_chunk_ids if c in evidence_ids]`)이 있는데, 이 평가로 그 필터가
실제로 작동한다는 것을 엔드투엔드로 확인했습니다.

두 평가 스크립트(9-2, 9-3) 모두 시작 시 `SUPABASE_PERSISTENCE=false`를 강제해 실제
Supabase 프로젝트에 테스트 데이터를 쓰지 않도록 격리했습니다.

## 10. 현재 한계

- 실제 금융기관 API 연동은 아직 아니며, mock SQLite 기반입니다.
- RAG는 로컬 corpus 기반 검색이며, 운영용 벡터 DB/semantic rerank는 추가 개선 영역입니다.
- 분쟁조정 사례/판례 수는 아직 충분하지 않습니다.
- 개인정보 마스킹과 저장 정책은 production 수준으로 추가 구현해야 합니다.
- 검색 Recall은 높아졌지만, 최종 판단 정확도는 별도 Support Accuracy 지표로 계속 검증해야 합니다.

## 11. 발표용 핵심 문장

> KB Key Buddy는 검색 결과를 곧바로 결론으로 쓰지 않습니다. 약관·규정·상품설명서는 직접 근거로, 분쟁조정 사례는 유사 사례 참고로, 민원 절차 문서는 다음 행동 안내로 분리합니다. 이후 Logic Verification과 Decision Gate가 근거 없는 결론을 `ask` 또는 `hold`로 막아 금융 민원 도메인에서 안전한 분석 흐름을 제공합니다.
